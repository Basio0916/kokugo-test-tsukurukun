## Context

リポジトリにはまだアプリのコードがない。体験はクリックできるモック（AI の返答は台本。`docs/reference/モック.html`、公開版は https://claude.ai/artifact/BbVTRYxp7zAHXG4VYKfSKD）で検証済みで、紙面の決まりごと（縦書き、本文の枠、傍線は文字の右、返り点は左下・送り仮名は右下、大問ごとの改ページなど）は `docs/reference/` のサンプル問題用紙と `openspec/config.yaml` の context にまとめてある。動機は proposal.md の Why を参照。

制約:
- ハッカソンの期間は約一週間。土台に使える時間は一〜二日。
- 先生は職員室の PC（Chrome や Edge が多い）でブラウザから使う。
- 後の change で AI（Claude API）を呼ぶ。API キーをブラウザに出さないため、サーバー側の関数を置ける構成にしておく。

## Goals / Non-Goals

**Goals:**
- 後の change がそのまま乗れるデータ構造と、データから紙面を描く流れを一本にする
- 番号・配点・配置をデータから計算し、紙面とデータが食い違わない構造にする
- AI が返す JSON を同じ形で検証できるよう、データの形を実行時にも検証できるようにする

**Non-Goals:**
- 長い本文を、大問の途中（本文の途中）で分けて複数ページに流すこと。この change では本文は一ページに収まる前提とする
- 紙の大きさの選択（A3 など）。この change は B4 横に固定する
- PDF の書き出し。印刷はブラウザの印刷機能に任せる
- Safari での見た目の作り込み（Chrome / Edge を基準にする）

## Decisions

### 1. 技術スタック: Vite + React + TypeScript、デプロイは Vercel
- 画面は編集中心のアプリで、検索流入やサーバー描画は要らない。Vite の SPA なら立ち上げが速く、構成も小さい。
- AI の呼び出しは後の change で Vercel Functions（`api/` 配下）に置き、ブラウザからはそれを呼ぶ。API キーはサーバー側だけに置く。
- 代替案: Next.js（App Router）。ルート処理やストリーミングを一つの枠組みで書けるが、サーバー描画やルーティングの仕組みはこのアプリには余分で、学ぶことと設定が増える。一週間の期間では小さい構成を優先する。
- Node は 24 系、パッケージ管理は npm。

### 2. データの形は zod で定義し、TypeScript の型はそこから作る
- テストのデータを zod のスキーマで定義し、型は `z.infer` で得る。読み込み時に検証して、配点の刻みや観点の値など、spec が「不正なデータ」とするものをはじく。
- 後の change で Claude が返す JSON も同じスキーマで検証できる。AI の出力を紙面に入れる前の関門になる。
- 代替案: 型だけ定義して検証を手書きする。依存は減るが、AI の出力を検証する段階で同じものを作り直すことになる。

### 3. 本文は「区切り（セグメント）の並び」で持つ
- 本文は `text`（地の文）、`mark`（傍線部。識別子と中身を持つ）、`ruby`（親文字と読み）の並びとして持つ。傍線部は文字そのものを包むので、後の change で本文を直しても、傍線は文字と一緒に動く。
- 漢文は句（行）ごとに、文字単位の並び（文字・送り仮名・返り点）として持ち、傍線部は文字の並びを包む。
- 問い文も区切りの並びで持つ。地の文、傍線部への参照（「傍線部①」の形か「①」だけの形か）、選択肢の範囲（「ア〜エ」）の三種類。番号は持たず、描くときに計算する。
- サンプルや試験データは、次の短い記法から区切りの並びに変換する補助関数で書く。補助関数はデータ作成用で、保存形式ではない。

  | 対象 | 記法 | 例 |
  |---|---|---|
  | 本文の傍線部 | `<m:識別子>…</m>` | `メロスは<m:a>激怒した</m>。` |
  | ルビ | `親字{よみ}` | `陸{くが}には源氏` |
  | 漢文の送り仮名・返り点 | `字(送り仮名)[返り点]`（どちらも省略可） | `春眠不[レ]覚(エ)[レ]暁(ヲ)` |
  | 漢文の傍線部 | 文字の並びを `<m:識別子>…</m>` で包む | `<m:a>花落(ツルコト)知(ル)多少</m>` |
  | 問い文の傍線部への参照（「傍線部①」の形） | `{傍線部:識別子}` | `{傍線部:a}「激怒した」とありますが` |
  | 問い文の傍線部への参照（「①」だけの形） | `{番号:識別子}` | `{傍線部:b}「揺りすゑ」・{番号:c}「漂へ」を` |
  | 問い文の選択肢の範囲（「ア〜エ」） | `{範囲}` | `次の{範囲}から一つ選び` |
  | 小問の項目の傍線（漢字の書き取りなど） | `[[…]]` | `友との[[ヤクソク]]を守る。` |

- サンプルの中身（本文・問い文・選択肢・正答・配点・観点）は、`docs/reference/モック.html` のデータ（`KANJI_SEC` `GRAMMAR_SEC` `DATA` `sakubunSec`）を正とする。モックは記法が少し違う（`<m1>` `{m1}` `{n:m1}` `{range}`）ので、上の記法に書き換えて使う。
- 代替案: 記法の文字列のまま保存する。書きやすいが、読むたびに解析が要り、型で守れない。位置（何文字目から何文字目）で傍線を持つ方式は、本文を直したときに位置の付け替えが要る。

### 4. 番号・配点・観点の集計は純粋な関数にする
- 大問の番号、問の番号、傍線部の番号（参照されているものだけを本文の順に数える）、選択肢の記号、大問の小計、観点別の合計、全体の合計は、テストのデータを受け取って結果を返す関数にまとめる。紙面のコンポーネントは結果を受け取って描くだけにする。
- 配点は 0.5 の倍数の数値で持つ。0.5 の倍数は浮動小数点でも誤差なく足せるので、整数への換算はしない。刻みに合わない値はスキーマの検証ではじく。
- 漢数字の表記（「二十四」「百」「〇・五」）も紙面用の関数として分けておき、単体テストする。

### 5. 縦書きは CSS（`writing-mode: vertical-rl`）で描く
- 傍線は文字の右側の線（インライン要素の右の罫線）、ルビは `<ruby>`、返り点と送り仮名は文字に重ねた小さな要素を左下・右下に置く。モックで見た目を確認した描き方を使う。
- 書体は教育向けの「BIZ UDMincho」（Google Fonts）を使う。読み込みに失敗したときは端末の明朝体で描く。
- 代替案: SVG や Canvas に自前で文字を並べる。組版を全部自分で書くことになり、ルビや禁則処理の手間が大きい。

### 6. ページ割り付けは「ブロックを測ってから詰める」
- 紙面を、表紙、大問の見出し（本文を持つ大問は見出し＋本文）、小問、の単位（ブロック）に分ける。
- 画面外で各ブロックを描いて、縦書きでの幅（列の厚み）を測る。ページの内側の幅に収まるまで前から詰め、次のブロックが入らなければ次のページへ送る。
- 文章を扱う大問と作文は新しいページから始める。一枚目は表紙と、先頭に続く漢字・文法の大問だけを載せる。
- 書体の読み込みで文字の幅が変わるので、書体の読み込み完了後にもう一度割り付ける。
- 代替案: 一度に全部描いて、はみ出した要素を後ろのページへ動かす（モックの方式）。動かすたびに測り直すので遅く、ページの境目が不安定になる。

### 7. 印刷は CSS の `@page` で B4 横を指定する
- 印刷時は操作部分を隠し、紙面の縮小を外し、ページごとに改ページする。`@page { size: 364mm 257mm; margin: 0 }` で余白は紙面側が持つ。CSS の `B4` は国際規格の B4（250mm × 353mm）を指し、日本の学校で使う JIS の B4（257mm × 364mm）と違うので、寸法を直接書く。
- 代替案: PDF を作ってから印刷する。正確だが、書体の埋め込みなどの手間が大きい。後の change で必要になったら足す。

### 8. 構成とテスト
- `src/model`（スキーマ、番号・集計の関数、記法の変換）、`src/paper`（紙面のコンポーネント、割り付け、漢数字）、`src/sample`（サンプルのテスト）、`src/App.tsx` に分ける。
- データと計算は Vitest で単体テストする。壊れやすい境目に絞る: 傍線部の番号（本文の順、参照されていないものは数えない）、問の番号、〇・五点の集計、刻みと観点の検証、漢数字。
- 紙面は Playwright で確かめる: 起動して全ページが表示される、どのページも文字がはみ出さない、傍線部と問い文の番号が一致する、印刷用の表示で操作部分が消える。

## Risks / Trade-offs

- [書体の読み込み前後で文字の幅が変わり、割り付けがずれる] → 書体の読み込み完了後に割り付け直す。Playwright のテストも読み込み完了を待ってから測る。
- [ブラウザごとに縦書きの描き方が違う] → Chrome / Edge を基準にする。Safari は後で確認する。
- [返り点・送り仮名の位置が、書体や文字の大きさで崩れる] → 文字の大きさに対する割合で位置を決め、Playwright のスクリーンショットで目視確認する。
- [本文が一ページに収まらないほど長い] → この change では本文を分割しない。サンプルは一ページに収まる。分割は後の change で扱う。
- [印刷の設定（倍率や余白）で紙面が崩れる] → `@page` で大きさと余白を指定する。崩れる場合の印刷設定は画面に案内を出す（後の change）。
