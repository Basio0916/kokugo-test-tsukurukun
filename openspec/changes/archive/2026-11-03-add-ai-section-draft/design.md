## Context

紙面はテストのデータ（`src/model/schema.ts` の `Test`）から決定的に描かれる。本文は区切りの並び（text・ruby・mark）で、問い文は記法（`{傍線部:id}` `{番号:id}` `{範囲}`）から `stem()` で区切りの並びに変換できる（`src/model/notation.ts`）。単元の指導事項は `findGroup(2, '走れメロス')` で引ける（`src/catalog/`）。いまアプリはサンプルのテストを定数として描いているだけで、状態も、サーバー側の処理もない。

制約:
- 締め切り 2026-11-08 20:00、提出物はデプロイした URL とデモ動画。この change は一〜二日で終える
- Vercel の関数の実行時間は、Hobby で既定・上限とも 300 秒（2026-08 時点の Vercel のドキュメント）
- 公開 URL にアクセス制限はかけない（決定済み）。API キーはサーバー側だけに置く

## Goals / Non-Goals

**Goals:**
- 一つの大問で「AI が作る → 検証 → 変換 → 紙面に出る」を、手元とデプロイした環境の両方で通す
- AI の返答を、紙面のデータに入れる前に必ず検証する関門を作る（後の change のチャットや小問の追加も同じ関門を通す）
- 生成にかかる時間と、検証に通る割合を実測する

**Non-Goals:**
- 本文の貼り付け、単元選び、小問ごとの作り直し、チャット（後の change）
- 古文・漢文の大問（ルビ・返り点を含む引用の扱いは後で）
- 項目を持つ小問（各◯点）と作文の問を AI に作らせること。この change で AI が作る解答形式は、記号選択・抜き出し・記述・短答の四つ
- AI の返答の逐次表示（ストリーミング）。数十秒の待ちは進み具合の表示で受ける

## Decisions

### 1. Claude の呼び出し方
- 公式 SDK `@anthropic-ai/sdk` の `client.messages.parse()` に、zod のスキーマを `output_config.format: zodOutputFormat(...)` で渡す（構造化出力）。返答はスキーマに合う JSON に制約され、SDK が `parsed_output` として検証済みの値を返す。
- モデルは `claude-opus-5-5`。思考は常に有効（このモデルでは止められない）で、深さは `output_config.effort` で決める。問題の質を優先して `high` から始め、生成時間を測って重ければ `medium` に下げる。
- `max_tokens` は 16000（ストリーミングしない呼び出しの目安）。
- 拒否（`stop_reason: "refusal"`）への備えとして、サーバー側のフォールバック（`fallbacks: "default"`、beta `server-side-fallback-2026-07-01`）を付ける。`messages.parse` と組み合わせられない場合は付けずに、拒否を失敗として扱う（実装時に確かめて tasks に残す）。
- 構造化出力が JSON スキーマで表せない制約（文字数など）は、SDK がスキーマから外して手元で検証する。それとは別に、変換後に既存の `Section` スキーマで検証する（Decision 4）。
- モデルは環境変数 `DRAFT_MODEL` で切り替えられる（既定は `claude-opus-5-5`）。Haiku には拒否時のサーバー側フォールバックがないので、Haiku のときは付けない。サーバーのログに一回ごとの時間と入力・出力のトークン数を出す。
- モデルの比較（2026-11-03、走れメロスの大問、effort `high`、同じ指示）:

  | モデル | 回数 | 一回の費用 | 時間 | 記号選択の正答 |
  |---|---|---|---|---|
  | Opus 5.5 | 2 | 約 0.08〜0.11 ドル | 35〜51 秒 | すべて正しい |
  | Sonnet 5.5 | 3 | 約 0.04 ドル | 28〜43 秒 | 3 回中 1 回で誤り |
  | Haiku 5.5 | 3 | 約 0.005 ドル | 26〜44 秒 | 3 回とも誤りあり（6 問中 5 問） |

  誤りは、どれも正答の番号が一つ後ろにずれたもの（`correct` を 1 から数えた）で、データの形は正しいので検証では見つからない。これを受けて、正答は選択肢の文で受け取る形に変えた（Decision 2）。Haiku は理由づけが本文にないなど、問いの中身にも問題があった。質を優先して Opus を採用する（費用はデモの回数ならハッカソンのクレジットで足りる）。
- 代替案: ツール呼び出しで JSON を受け取る。このモデルでは `tool_choice` で呼び出しを強制できない（400）ので、呼ばれなかった場合の処理が要る。構造化出力のほうが単純。

### 2. AI の返答の形（`src/ai/proposal.ts`）
```
SectionProposal {
  marks: [{ key: "A", quote: "本文からそのまま引用した文字列", before?: "直前の数文字" }]
  questions: [{
    format: "choice" | "extract" | "description" | "short"
    stem: "記法で書いた問い文"          // {傍線部:A} {番号:A} {範囲} を使う
    choices?: string[]; correctChoice?: string  // 記号選択。正答は選択肢の文そのもの
    charLimit?: number                     // 抜き出し・記述・短答
    answer?: string; rubric?: string[]     // 正答・模範解答・採点の観点
    kanten: "knowledge" | "thinking"
    standard: string                       // 指導事項の記号（C(1)イ など）
    weight: number                         // 配点の重み（1〜5 の整数）
    rationale: string                      // この問いを入れる理由（先生向け、一〜二文）
  }]
}
```
- 識別子・番号・配点の点数は持たせない。傍線部は AI が付けたキー（A, B…）で問い文から参照し、変換時にシステムの識別子に置き換える。
- 引用が本文に二回以上現れるときのために、直前の数文字（`before`）を任意で持たせる。
- 記号選択の正答は、番号ではなく正しい選択肢の文で受け取り、システムが選択肢と照らし合わせて番号を決める。一致しなければ不正として作り直させる。番号で受け取ると、0 と 1 のどちらから数えたかで一つずれても形は正しいので検証で見つからず、模範解答の間違ったテストが紙面に出てしまう（モデルの比較で Sonnet・Haiku に実際に起きた）。
- 問い文に ①〜⑳、「ア〜」のような番号・記号の文字があれば不正とする（記法を使わずに番号を書いた印）。

### 3. 引用から傍線部を付ける（`src/ai/anchor.ts`）
- 既存の傍線部を外して、本文を text と ruby だけの並びに戻す。ルビの親文字と地の文をつないだ「平文」と、平文の各文字がどの区切りの何文字目かの対応を作る。
- 引用を平文の中で探す。見つからなければ不正。二回以上あれば `before` で絞り、それでも一つに決まらなければ不正。
- 見つかった範囲の両端で text の区切りを分け、範囲の区切りを mark で包む。端が ruby の親文字の途中にかかる場合は不正（ルビを割らない）。傍線部どうしが重なる場合も不正。
- 純粋な関数にして単体テストする（見つかる・見つからない・二回ある・ルビをまたぐ・ルビを割る・重なる）。

### 4. 返答からテストのデータへの変換と検証（`src/ai/toSection.ts`）
- 傍線部を付けた本文、記法の問い文を `stem()` で変換したもの（キーをシステムの識別子に置き換えてから）、配点（Decision 5）で `Section` を組み立て、既存の `Section` スキーマで検証する。小問の識別子はシステムが振る。
- 検証の失敗は、AI に返せる日本語の理由の並びにまとめる（「問三: 記号選択なのに選択肢がない」など）。

### 5. 配点の割り振り（`src/ai/points.ts`）
- 大問の現在の小計を保つ。重みに比例した値を刻みの単位で切り捨て、残りを端数の大きい順に一刻みずつ配る（最大剰余方式）。端数が同じなら前の小問を優先して、結果を決定的にする。
- どの小問も最低一刻みは持つ。小問の数×刻みが小計を超える場合は不正として作り直しの対象にする。

### 6. サーバー側の関数（`api/draft-section.ts`）
- Web 標準の `Request` を受けて `Response` を返す関数にする（Vercel の Node ランタイムの書き方）。入力は大問のデータ（本文・種類・指示文・現在の小計）、学年、教材名、配点の刻み。単元の指導事項はサーバー側で `findGroup` から引く。
- 呼び出し → 検証・変換 → 失敗なら理由を添えて一度だけ作り直し → 結果（`Section` と小問ごとの理由）か失敗の理由を JSON で返す。検証と変換は `src/ai/` の関数をそのまま使う。
- `maxDuration` は 300 秒（Hobby の上限）。
- 手元の開発は、Vite の開発サーバーに小さなプラグインを足し、`/api/draft-section` への要求を同じ関数に渡す。`npm run dev` だけで動き、Vercel CLI は要らない。API キーは `.env.local` から読む（`.gitignore` 済み）。
- 代替案: `vercel dev`。Vercel CLI のログインとプロジェクトの紐付けが手元でも要り、Vite の開発サーバーと二重になる。

### 7. 画面
- `App` がテストを状態として持ち、大問を置き換えられるようにする。紙面（`Paper`）は今まで通りテストを受け取って描くだけ。
- 文章を扱う大問の見出しの横（紙面の外、印刷されない場所）に「AI に大問を作ってもらう」ボタンを置く。この change では画面の上部のバーに、対象の大問を選ぶ形でもよい（紙面の上に重ねる UI は後の change で作るので、ここでは最小にする）。
- 作っている間は「作っています（数十秒かかります）」を表示してボタンを押せなくする。失敗したら理由を表示し、紙面は変えない。
- 作った後、紙面の横に小問ごとの理由の一覧を出す。指導事項が単元の指導事項にない小問には「単元の指導事項にない」と示す。

### 8. テスト
- 単体テスト（Vitest）: 引用からの傍線部、配点の割り振り、返答から `Section` への変換と検証の失敗理由。AI の返答は手で書いた固定の値を使う。
- E2E（Playwright）: `/api/draft-section` を `page.route` で固定の返答に差し替え、ボタン → 作っている表示 → 紙面の小問が置き換わる → 理由の一覧、と、失敗の表示を確かめる。本物の Claude は呼ばない。
- 本物の呼び出しは手元で数回だけ試し、生成時間と検証に通ったかを tasks に記録する。デプロイ後に公開 URL で一回試す。

## Risks / Trade-offs

- [生成が遅く、待ちが長い] → 実測して effort を調整する。300 秒を超えるなら小問の数を減らす。逐次表示は後の change で検討する。
- [AI が本文の文字を少し変えて引用し、傍線が付かない] → 指示で「本文をそのまま引用する」と明示し、失敗したら見つからなかった引用を理由として作り直させる。
- [問い文の記法の書き間違い] → 変換時に検出して作り直しの理由にする。
- [公開 URL を誰でも叩けて費用がかさむ] → アクセス制限はかけない決定。Anthropic のコンソールで使用量の上限を設定しておくことを勧める（ユーザーの操作）。
- [Vercel のプロジェクト作成と環境変数の設定はユーザーのアカウントでの操作が要る] → tasks に、ユーザーに頼む手順として書く。
- [フォールバックの beta と `messages.parse` の組み合わせが使えない] → 付けずに進め、拒否は失敗として表示する。
